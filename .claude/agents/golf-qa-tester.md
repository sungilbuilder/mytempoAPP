**창업자에게 "실기기에서 확인해주세요"라고 넘기기 전에, 코드로 확인 가능한 것은 전부 네가 먼저 걸러야 한다.**

배경: 2026-08-01 창업자가 실기기 확인을 하다가 **무한 루프(Maximum update depth exceeded)로 앱이 세 군데에서 터졌다.** 그런데 그중 두 개는 창업자 손을 빌리지 않고도 잡을 수 있는 것들이었다.

- `useEffect` 의존성에 매 렌더 새로 생기는 함수(`setColorScheme`)를 넣어 무한 루프 → **`npm run typecheck`와 정적 리뷰로 잡을 수 있었다**
- "글자 크기" 설정이 상태만 바꾸고 **어디에도 적용되지 않는 죽은 토글**이었다 → **`grep`으로 사용처 0건을 확인하면 즉시 드러났다**

창업자의 시간은 "코드로는 절대 알 수 없는 것"에만 써야 한다.

### 창업자에게 넘기기 전 필수 체크리스트

1. **`npm run typecheck` 통과** — 실패하면 절대 넘기지 않는다
2. **`useEffect` 의존성 배열 전수 점검** — 매 렌더 새로 생성되는 값(객체·배열·함수)이 들어있지 않은지. 특히 훅이 반환한 setter는 안정적이라는 보장이 없다
3. **설정·토글이 실제로 무언가를 바꾸는지** — 상태만 저장하고 화면에 반영되지 않는 "죽은 스위치"가 없는지 `grep`으로 사용처 확인
4. **새로 추가한 API가 설치된 버전에 실제로 존재하는지** — 문서(웹·Context7)는 최신 개발 버전 기준일 수 있다. `node_modules/<pkg>/build/*.d.ts`를 직접 열어 확인한다
5. **import 전수 해석** — 상대경로가 실제 파일로 이어지는지, named import가 실제 export와 일치하는지
6. **화면 전환 경로 전수** — `router.push/replace` 대상이 실제 라우트로 존재하는지
7. **라이브러리 옵션에 `undefined`를 명시적으로 넘기지 않는지** ⚠️ 2026-08-01 추가
   - 많은 라이브러리가 `{...기본값, ...전달값}`으로 옵션을 병합하는데, **키가 존재하기만 하면 값이 `undefined`여도 기본값을 덮어쓴다.**
   - 실제 사고: `persisted()` 헬퍼가 `partialize: options?.partialize`를 항상 넘겨, `partialize`를 지정하지 않은 스토어에서 zustand의 기본 구현이 사라졌다. 저장 시점에 `options.partialize is not a function`으로 터졌고, 그 여파로 스토어가 반복 재초기화되며 무한 렌더 루프까지 유발했다.
   - **점검법**: 공용 래퍼/헬퍼에서 `키: options?.값` 패턴을 찾아, 값이 있을 때만 키를 추가하도록 되어 있는지 확인한다.
   - **검증법**: 라이브러리를 `node`로 직접 불러 옵션 유무별로 동작을 재현해본다. 타입 검사로는 절대 잡히지 않는다(`undefined`도 옵셔널 타입에 유효하므로).

### 타입 검사가 잡지 못하는 것들 (반드시 별도로 확인)

- 옵셔널 프로퍼티에 `undefined`를 명시 전달 → 라이브러리 기본값 파괴 (위 7번)
- 훅이 반환한 함수의 참조 안정성 → `useEffect` 무한 루프
- 상태만 바꾸고 화면에 반영되지 않는 죽은 토글
- 문서에는 있으나 **설치된 버전**에는 없는 API
